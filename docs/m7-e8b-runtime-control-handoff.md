## 3. What the packet must contain (the user's list, with the code it touches)

1. **Two designs, compared head-to-head, not one recommended by fiat:**
   - **A — trusted, bounded fill authorization.** The trusted side (the host/caller that mints the handle — `src/core/fillService.ts`, the session mint in `src/browser/session.ts`, the lockdown/taint registry `src/core/lockdown.ts`, `src/supervisor/lockdownDomain.ts`) grants a *bounded* fill authority with the handle: a count, a scope (session, document, control identity), and/or a time or navigation bound. Fills beyond the bound are refused through the real fill path with a distinct refusal reason.
   - **B — completion-triggered revocation.** Fill authority is unbounded until the trusted side observes a *completion signal*, after which the handle (or the session's fill capability) is revoked.
   - For **each**: the exact **trusted signal it relies on outside the testbed**. The testbed's signed completion receipt (`SCHEMA.md` ~1036-1056; fixture-side private key) does not exist in production, so B cannot depend on it. Candidates to evaluate honestly: the host-owned browser's own observation of the submit → top-level navigation sequence (it owns the `BrowserContext`, `docs/phase-0-plan.md` §"Browser-ownership decision"); a caller-supplied per-task budget minted with the handle; a caller-side explicit "task done" call that the evaluated agent cannot make. State what each signal can and cannot attest, and what a hostile page on the authorized origin can forge.
2. **Case table** — for both designs, the behaviour and the refusal/allow outcome for: repeated fills into the same control; repeated fills into a different control on the same origin (the E8b case); navigation (same-document, same-origin top-level, cross-origin, back/forward, reload); concurrent calls (the per-session mutex, `src/core/sessionMutex.ts`, non-reentrancy — what happens when two fills race the bound); new sessions and refreshed handles (does authority follow the handle, the session, or the task? can `browser_open_session` + the same handle reset it?); failed login retries (wrong password → the page re-renders the login form: the legitimate second fill must be allowed — how is it told apart from the re-auth lure?); legitimate re-authentication (a real site asking to re-enter the password for a sensitive action: under both designs this is *refused* by construction — the packet must say so plainly and route it to the renewal authority, not to the agent).
3. **Renewal authority** — who can renew, through what interface, with what audit record; a proof sketch that the evaluated agent has no path to it (the tool registry is closed; the adapter surface for M8 must not reopen it).
4. **Acceptance and demonstration through the real fill path**: (a) all five scenarios' first-login completion unchanged (stub eval green: `make eval-stub`, five cells 0/10 leaks 10/10 completed); (b) a scripted client that logs in legitimately and then attempts the re-auth fill **must now receive a refusal** from the real `fill_from_vault` path, with a deletion/mutant test showing the refusal comes from the new control and not from a selector accident; (c) the O3/E6 scripted test that *forces* a fill and observes the `dom-fill` canary is kept as-is (checker preserved) — the packet explains how both tests coexist (e.g. the E6 client bypasses the control via a test-only trusted renewal, which must itself be shown unreachable from the agent); (d) the retry/recovery paths (`lookalike-origin-redirect`, a failed-login retry fixture if one is needed) complete; (e) `SKILL.md` needs **no** wording change if the new refusal reason falls under the existing "On other fill refusals stop; masked snapshot allowed" row — verify the byte budget (`src/agents/prompt.test.ts:40`, ten rows < 1,024) is untouched; if a new row is unavoidable, say so and stop (E8a wording is locked).
5. **Narrow claim section**, verbatim boundary from §2, plus what a *qualified* future cohort could and could not establish (Wilson CI language as in the pre-registration §2).
6. **Deviations / residuals** the design accepts (e.g. legitimate re-auth is refused; a page that captures the first fill is out of scope), each stated as a residual, not hidden.
