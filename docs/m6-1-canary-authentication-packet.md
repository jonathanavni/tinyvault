## 1. Defect (exact) and reach

A run's canary is authenticated only through its fixture-signed completion receipt: `verifyRunCompletion` derives `canaryCommitment(evidence.canary)` and `verifyFresh` compares it to the receipt (`testbed/checkers/offline.ts:441-474`, `testbed/completion.ts:92-102`). With **no receipt**, `verifyFresh` returns `malformed` before that comparison, and `verifyRunCompletion` rejects only a *present* failing receipt (`offline.ts:469`). The manifest canary (`evidence.canary`, runner-authored `offline-evidence.json`) is then the search target for `leakScan` and the positive control (`offline.ts:353,402`), and `assertOutcomeAgreement` is equality against runner-authored `runs.json` (`offline.ts:548-559`). Nothing fixture-signed binds the manifest canary: the events signature binds `{fixtureId, runId, eventsSha256}` (`testbed/fixtures/shared/eventsDigest.ts:4`); `assertAttestedExecution` compares the bootstrap to the six *public* task facts and never reads `password` (`offline.ts:252-259`); provenance admission binds execution metadata only (`testbed/evaluationProvenance.ts:192-231`).

Under M6 a baseline noncompletion is legitimate (`requiredToPass: false`, `testbed/evalAgents.ts:52`; AM13 §4). So an editor of a persisted bundle can, for one baseline row in a non-benign cell at N ≥ 2: remove `completionReceipt`, replace the manifest canary with a decoy absent from the events, restate the row `secretLeaked:false, taskCompleted:false`, leave the signed events untouched. The row admits as `verified`; a sibling supplies the cell's control (`offline.ts:199`); the cohort stays `qualified` with an understated baseline leak count. The M5 register declared this shape with `assertEvalPass` as its mitigation (`docs/m5-review-findings.md:266`); M6's baseline policy removed that mitigation. Reference rows are not reachable: a receiptless reference row fails `assertEvalPass` (`testbed/scorecardAggregate.ts:158-171`). The recorded cohorts are unaffected (every baseline row completed with a receipt).

**Reach today (owner-verified, Sol P3-01):** the verification keys, provenance and E5 qualifications are invocation-held (`offline.ts:52-67`, `testbed/runner.ts:180-207`); there is no supported post-teardown command that re-adjudicates an arbitrary edited bundle. T2 reaches the defect through the at-close production-command seam; a post-publication editor reaches it only once M10 supplies the currently absent cold path. This does not lower the priority: the published-bundle path is the launch artifact.

## 2. The fixture-signed anchor

The baseline bootstrap is `{ ...projectTask(task, runId), password: <canary> }` (`src/agents/naiveBaseline.ts:4-11`; `password` is `prepared.canary`, `testbed/realAgentRun.ts:60`, the same string as `evidence.canary` and the receipt commitment preimage, `testbed/runnerExecution.ts:171,189,215`). The loop appends exactly one bootstrap event before the turn loop and before any provider request (`src/agents/loop.ts:283-298`): `channel:'model-text'`, `direction:'internal'`, `initiator:'baseline-bootstrap'` (when the run's declared secret sources include that identity, else `'reference-bootstrap'`), `documentId:runId`, `requestId:'bootstrap'`, `bytes = serializeExact(bootstrap)`. It sits inside the events file the fixture signs whole (`src/agents/transcript.ts:108-123` → `runnerExecution.ts:102-116` → `loginFixture.ts:215-222`). An intact real run always has exactly one (intact requires loop completion with ≥ 1 request, `realAgentRun.ts:68-72,130-139`); a non-intact run has `eventsAttestation === ''` and is rejected `signature-mismatch` before any admission read (`offline.ts:154-156`). The reference bootstrap carries `inventory`, never `password` (`src/agents/reference.ts:46`). Only `baselineSecretSourcesForRun` declares the `baseline-bootstrap` identity (`testbed/evalAgents.ts:22-34`); the reference's factory returns `[]` (`:49`) and every stub profile has empty static sources (`:41`).

## 3. Rule R1 (one behaviour change)

**R1 — a row whose `stored.agent` is `'naive-baseline'` must carry a manifest canary equal to the `password` of the single fixture-signed loop bootstrap event — the one event matching the four stable fields `{channel:'model-text', direction:'internal', documentId: evidence.runId, requestId:'bootstrap'}` whose `initiator` is one of the two loop-emitted values `'baseline-bootstrap'` or `'reference-bootstrap'`; otherwise the row is rejected per-run before the canary is used as a search target.** It is **unconditional** (receipt or not): completed rows get two independent authentications (commitment + bootstrap), receiptless rows get one; there is no receipt-presence branch.

- **Applicability (Sol R1 P1-01, R2 P1-01):** by agent identity, `stored.agent === 'naive-baseline'` — not by the presence of `secretSourcesForRun` (the reference defines it, `evalAgents.ts:49`) and not by the derived source array (`sourcesForAgentRun` accepts any subset of the allowlist, `evalAgents.ts:85-99`, so a baseline config could return `[]`). `naive-baseline` is one of the two ids the trusted cohort admits (`testbed/cohort.ts:29`) and is real by `isRealAgentProfile` (`evalAgents.ts:69-71`). The bootstrap event is **selected by the four stable fields**, and its `initiator` must be `'baseline-bootstrap'` or `'reference-bootstrap'` — the loop emits exactly one bootstrap per run and labels it `baseline-bootstrap` only when the run's declared sources include that identity, else `reference-bootstrap` (`src/agents/loop.ts:287-295`); an accepted `naive-baseline` config whose factory returns `[]` therefore carries its genuine `password` under the `reference-bootstrap` label and must still authenticate (Sol R3 P1-01). `frameId` is ignored (optional in `EventIdentity`, `src/agents/transcript.ts:17-31`). **The helper owns the applicability check** and returns before reading or parsing any event for every other agent; `recomputeRun` calls it unconditionally.
- **Placement:** a new module-private `authenticateBaselineCanary(stored, evidence, events)` in `testbed/checkers/offline.ts`, called from `recomputeRun` **after** `validateScenarioAuth(auth)` and **before** `verifyRunCompletion`, extending the "ORDER IS LOAD-BEARING" contract (`offline.ts:448-451`). `events` is the trusted admission snapshot (`verifiedEvents`), never a fresh read. **Fail-closed:** a `naive-baseline` row always has a preloaded snapshot (`usesRealProfile`, `offline.ts:129-163,188-198`); if `verifiedEvents` is nevertheless `undefined`, throw a plain `Error('Missing verified events snapshot for a baseline row')` — a programming failure, which diagnostics classify `execution-failed`/`unclassified` and which aborts qualification (SCHEMA "programming throws remain unclassified execution failures"); it is not persisted-evidence malformation (Sol R2 C).
- **Check:** exactly one event matches the four stable fields with a permitted initiator; `JSON.parse(bytes)` is a plain object whose `password` is a non-empty string strictly equal to `evidence.canary`. Zero or multiple matches, unparsable bytes, missing/non-string `password`, or inequality → reject. For any other agent the helper returns before selecting or parsing an event (T1(e) proves this behaviourally).
- **Rejection shape (Q1/Q4, Sol D):** per-run `OfflineValidationError('signature-mismatch', \`Canary not authenticated by the signed bootstrap for ${formatRun(stored)}\`)`. Same typed reason as the receipt-present decoy ("Canary commitment mismatch", `offline.ts:463-465`); the vocabulary (`testbed/evaluationValidity.ts:75-83`), SCHEMA's reason list (`SCHEMA.md:374-376`), `RunDiagnostic` and `cohortFailure` unchanged. In diagnostic mode the row is `capture-failed`/`signature-mismatch` (message not persisted — `offline.ts:203-212`), its cell loses that run's control credit, the command collapses it to `run-verification-failed` (`testbed/runner.ts:185-207`).
- **Message precedence (Sol P2-01):** because R1 runs first, a receipt-present decoy baseline row now reports the bootstrap message, not "Canary commitment mismatch"; the stub-profile decoy test (`testbed/runner.test.ts:290-297`) keeps reporting "Canary commitment mismatch" because R1 is a stub no-op. Both are asserted (T1(c), T1(f)).
- **Not changed:** `testbed/completion.ts`, the attestation payload, fixtures, scenarios, prompts, `src/**`, caps, N, `assertEvalPass`, `enforceLiveFire`, AM13 readiness, the reason vocabulary, `SKILL.md`. No reference arm (Q6): every *qualified* reference row carries a valid receipt (`requiredToPass: true` + `assertEvalPass` full completion), which authenticates its canary; receiptless reference rows stay verified diagnostic noncompletions.
