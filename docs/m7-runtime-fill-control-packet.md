## 3. The two designs

Both designs share the trusted unit — **the host** (one `createSupervisedHost` call: one run in the testbed, one adapter process in M8) — and the handle-keyed subject (fact 3). They differ in *when* authority ends and in *what signal* ends it.

### 3.1 A — trusted, bounded fill authorization

The trusted side grants, with the authorization domain (one per host via `createSupervisedHost`), an **initial budget of exactly one password injection per handle; total authority is one plus explicit constructor-side renewals** (§6.3). A fill consumes the budget when the realm reports `assigned: true` **or** when the injection's transport failed (fact 16: the value may be in the page — fail-closed); every refusal decided before injection and every injection outcome that assigned nothing to the DOM (`origin`, `identity`, `too-long`, `unplaceable`; fact 16) leaves it untouched. A request whose handle has no remaining budget is refused through the real fill path with a distinct closed reason, **before the secret is resolved**. Only the control-plane lifecycle, held by whoever constructs the authorization domain and never by `host.tools`, can grant a further fill (§6.3).

- **Trusted signal outside the testbed:** *none about the page's state.* The inputs are the host's own bookkeeping — which handle was injected, how many times, in this host — and the composer's grants. The only page-controlled input is whether an in-flight injection's transport survives, and that case is resolved fail-closed.
- **What a hostile authorized-origin page can forge:** nothing that increases the count's permissiveness. It can **destroy** the budget — end its document mid-injection, or hold the injection open past the host's 10 s bound so the forced disposal turns it into `transport` — before any value is assigned: fail-closed, the first login then cannot complete in that host, and the agent's transcript shows the refusal. This is deliberately triggerable, not only accidental (§6.7 (d), R10); it is available only to a page hostile *at fill time on the login document*, which could already read the fill instead (R4), so it adds no confidentiality capability beyond R4 — but it is a distinct first-login denial, and remains subject to O-RC-6.
- **What it cannot distinguish:** a legitimate second fill (transient login failure, session loss after an assigned fill, real re-authentication) from the lure. Both are refused; both route to the renewal authority (§6.3), never to the agent. §6.7 puts this to the user.

### 3.2 B — completion-triggered revocation

Fill authority is unbounded until the trusted side observes a **completion signal** for a document that received an assigned fill; then the handle is revoked for the host. The production-available signal candidates, evaluated honestly:

- **B1 — host-observed document end:** an assigned fill in document epoch *e* of a session, followed by the main-frame `Page.frameNavigated`/`Page.documentOpened` that ends epoch *e* (the exact hook that clears the lockdown today, fact 2), or the page's close. *Attests:* the filled document ended. *Does not attest:* that a login was submitted, accepted, or even attempted. *Forgeable by a hostile authorized-origin page:* **suppressible** — a page that submits with `fetch` and re-renders in place never ends its document (fact 14), so a lure rendered *in the same document* after a fetch-based login keeps the handle live; also triggerable early (fail-closed, harmless — including on a failed navigation's error-page commit, fact 14).
- **B2 — caller-side explicit "task done" call outside the tool registry:** the composer tells the host the task is complete. In the testbed the runner does not know completion (verified offline from the receipt); in M8 the adapter's parent is the harness, whose belief comes from the model's own "done" — the untrusted party. **Collapses into A or into trusting the agent.**
- **B3 — host-observed request:** the host already observes every request, including `fetch`, through its own CDP `Network.requestWillBeSent` hook (fact 17), so this signal is **not** page-suppressible (rev 0 said otherwise; corrected). It is rejected for two other reasons: it attests *submission*, not a completed login (a 401 or a 200-with-error is also a request), so "success" would be a site-specific heuristic; and recognising *the credential's* request rather than any POST requires the trusted side to compare an outgoing body against the plaintext secret — a secret-dependent branch on the caller path that the noninterference work (`docs/phase-0-plan.md:640`) exists to keep absent.
- **B4 — the signed completion receipt:** testbed-only (fact 12). Excluded by the handoff.

B is specified with B1 for the comparison. Revocation would attach to the existing lifecycle hook (`resetDocument`/`closePageState`) and a per-session record `{epoch, handle}` written at assignment.

## 5. Comparison and recommendation

**D-RC-1 — adopt A.** The decisive rows are 3 and 4: B's document-end signal (B1) is suppressible by the very party it is meant to constrain — a page on the authorized origin decides whether its document ends — so B blocks the E8b lure only because the fixture happens to redirect; a page that logs in with `fetch` and renders the re-verification prompt in place defeats B and not A. B's request signal (B3) is not suppressible but cannot distinguish a successful login from a failed one without a site-specific heuristic, and cannot identify the credential's request without a secret comparison on the caller path. B buys nothing on the failed-login retry either: a form re-render is a navigation (row 10), so B refuses it too. **No production completion signal is both unsuppressible and free of a secret-comparison surface; A needs no signal at all**, blocks a strictly larger class, and is smaller to implement (a counter and a reservation, no CDP coupling). Its cost is the same as B's on every legitimate second-fill case — both refuse — so A's cost is not a reason to prefer B; that cost is put to the user in §6.7.

Rejected variants, recorded: **A-session** (budget per session) — bypassed by close + open (fact 5). **A-document** (budget per document) — the E8b lure is a new document. **B2** — reduces to trusting the agent's "done" or to A. A hybrid "A plus B1 as an additional revocation" adds a CDP dependency and a second state machine for no additional blocked case. **A with a path-bound retry grant** and **A with a status-bound retry grant** are analysed and rejected in §6.7.

## 6. Design A — the contract (owner recommendation; rev 1)

### 6.1 Types and placement (mirrors the lockdown split, fact 2)

- `src/core/fillAuthorization.ts` (new, core; no import edge into `src/supervisor`): a data-plane capability `FillAuthorization = { reserve(handle: Handle): FillReservation | null }` with `FillReservation = { commit(): void; release(): void }` (one-shot and **total**: the first of `commit`/`release` wins, the second is a no-op, neither throws), and a control-plane capability `FillAuthorizationLifecycle = { renew(handle: Handle): void }`. Both are frozen objects, no free text.
- `src/supervisor/fillAuthorizationDomain.ts` (new, supervisor composition root): `createFillAuthorizationDomain()` → `{ authorization, lifecycle }`. State per handle in a `Map<Handle, …>` (never a plain object): `granted` (default 1), `consumed`, `reserved`. `reserve` returns `null` when `granted − consumed − reserved ≤ 0`, else increments `reserved` — one synchronous read-modify-write, no `await` inside. `commit`: `reserved−1`, `consumed+1`. `release`: `reserved−1`. `renew`: `granted+1`. Counters are never returned to a caller (round 1: rev 0's `consumedCount()` is withdrawn; tests observe behaviour, §7.1).
- `createFillService` gains a **required** option `authorization: FillAuthorization` (**D-RC-2**: required, so an omitted authorization is a compile error, never a silently unbounded service; fact 15 lists the eight callers). `createSupervisedHost` creates the domain beside the lockdown domain (`host.ts:72`) and passes `authorization` at `:85`; `composeSupervisedHost` parts are unchanged (the fill service arrives prebuilt — see §6.3 for what that implies).

### 6.2 Enforcement order and settlement in `continueWithDestination` (`fillService.ts:162-204`)

epoch re-check → `isLocked` (`locked-field`) → **`reserve(handle)`; `null` → `finish('handle-exhausted')`** → `lock` → `resolveSecret` → `isLocked` re-check → `inject` → `completeInjection`. **Implementation shape (round 2):** the existing single `try` at `:173-180` is split — a first `try`/`catch` around the `isLocked` check alone (keeping `locked-field` and the `InvalidControlIdentityError` → `staleOutcome` mapping ahead of the budget; `reserve` must never precede `isLocked`: `src/core/fillService.browser.test.ts:557-560` pins `locked-field` for a third fill of a locked control), then `reserve`, then the settlement guard `try { <the lock try/catch, resolveSecret, the isLocked re-check, and the existing inner try/finally { secret.clear() } unchanged> } finally { settle() }`. **Invariant R (settlement):** the guard records the injection outcome into a local the moment `inject` returns, before `completeInjection`; its `finally` calls exactly one of: `commit()` when the recorded outcome is `assigned: true` **or** `assigned: false, reason: 'transport'` (fact 16); `release()` otherwise — every refusal after `reserve`, every throw **before `inject` returns** (`InvalidControlIdentityError` from `lock`, backend failure from `resolveSecret`, the `isLocked` re-check, a rejected `inject`), and every outcome that assigned nothing to the DOM (`origin`, `identity`, `too-long`, `unplaceable`). **After `inject` returns, the recorded outcome controls settlement even if `completeInjection`, `finish` or `secret.clear()` throws** — "the recorded outcome decides, not the returned result." The `try`/`catch` around `lock` inside the guard is *new* (today's single `catch` at `:176-180` serves both `:174` and `:175`). A rejected `inject` releases **because** the port contract admits exactly one rejection cause, thrown before any browser call, and the real implementation cannot reject after `secret.consume()` succeeds (fact 16); T-RC-5 pins that contract. Settlement methods are total (§6.1), so the guard cannot itself throw. **Invariant S:** `reserve` precedes `resolveSecret` (`:183`), the only site that materialises the plaintext for this request; the tree's single `Secret.consume()` site is `src/browser/session.ts:521`, pinned by `src/core/fillService.structure.test.ts:12-15`, and is reachable only through `inject` at `:196` — so an exhausted handle's secret is neither decrypted nor consumed (the policy read at `:130` and the DOM pin at `:152` still happen — no secret, row 14). Placing `reserve` after the origin checks (`:145-149`) and the pin (`:150-156`) gives the existing refusal precedence, so the lookalike's first request and every row-14 refusal consume nothing.

### 6.3 Renewal authority

- **Who:** whoever constructs the authorization domain. In production that is `createSupervisedHost`, which hands the lifecycle to its caller **only** through a new optional option `onFillAuthorization?(lifecycle: FillAuthorizationLifecycle): void`, invoked once during composition. The lifecycle is **not** a property of `SupervisedHost`, not in `host.tools`, not in `EVALUATED_AGENT_TOOLS`, not a case of `invokeHostTool`. A second route exists and is stated plainly (round 1): `composeSupervisedHost` (`host.ts:93-99`) takes a prebuilt fill service, so any caller that builds `createFillService({…, authorization})` holds the domain it created, without ever naming the option. Today `composeSupervisedHost` has **no non-test call site at all** (fact 4); T-RC-10 (c) pins that. A structurally-typed always-granting `authorization` literal names none of the four identifiers T-RC-10 (a) inventories; that route is closed by (c) together with (e) — `createFillService`'s only non-test call site is `host.ts:85` — and (f) — `createSupervisedHost`'s option-key set is pinned and no `authorization` property appears at any non-test host-construction or `createHost` site — and, in M8, by §6.6 (1) and M8's own single-composition pin.
- **In the testbed:** `runnerExecution.ts` does not pass the option and does not compose directly (pinned, T-RC-10), so no run — stub or real — can renew; the O3/E6 test obtains the lifecycle through the test kit's `composeHost` seam (§7.1 T-RC-2) and calls `renew(handle)` in `onResult` after the `success` snapshot, before `reauth-fill`.
- **In M8:** the adapter composes through `createSupervisedHost` without the option, never through `composeSupervisedHost` or a directly constructed fill service (pinned, T-RC-10, and listed in M8's leave-alone set, §6.6). Renewal in M8 v1 is a restart of the adapter process by its parent (R12, O-RC-8). A stdio method for renewal is **explicitly rejected**: the MCP client relays model requests, so any such method is a model-visible renewal tool (handoff §2).
- **Audit record:** none is added (D1 territory, out of scope; **O-RC-3** asks the user to accept this). In the testbed a renewal is visible only in test code; the run transcript shows every `fill_from_vault` result, so a second `{ ok: true }` for one handle in a cohort transcript is an alarm — it cannot by itself distinguish an authorized renewal from a control that did not fire (R13), which is why T-RC-1 is the in-tree absence detector (§8.3).
- **Proof sketch that the evaluated agent cannot renew or bypass:** (i) the loop rejects any tool not in the frozen registry (`loop.ts:455-487`; digest pinned, fact 4); (ii) the runner's switch has seven cases and a throwing default (`runnerExecution.ts:461-474`); (iii) `host.tools` is frozen and carries no lifecycle (`host.ts:333-354`; T-RC-10 (b) pins its exact keys); (iv) the lifecycle is reachable only by code that *constructs* the domain — `createSupervisedHost` (handing it out only via the option) or a direct composer — and no value reachable from `SupervisedHost` or `host.tools` carries it (T-RC-10 (b), a recursive cycle-safe traversal plus invocation of the safe zero-argument accessors; a lifecycle smuggled inside a closure or returned from `finish`/`closeAll`/`abort` is beyond any reflection pin and is guarded by (g)'s AST assertion and by review of `host.ts` — R19); the only non-test constructor is `createSupervisedHost` (T-RC-10 (a), (c), (d), (e), (f)); (v) sessions do not scope the budget (fact 5, row 8); (vi) handles cannot be refreshed and `list_vault` is not model-visible (fact 3, row 9); (vii) `reserve` is a synchronous check-and-increment with no suspension between the read and the write, so the awaits that precede it (`:122`, `:130`, `:152`) cannot interleave two reservations of one unit (row 7); (viii) `transport` commits and every other non-assigned outcome returns before the value setter, so there is no "assigned then released" shape and a page cannot recover a unit by ending its document mid-injection (fact 16, row 6) — it can only destroy one (§6.7 (d)).

### 6.7 The first-login recovery decision (O-RC-6) — where the handoff and both designs conflict

The handoff (§2: "any failed-login retry must still complete"; §3.2: "the legitimate second fill must be allowed — how is it told apart from the re-auth lure?") asks for something neither design can give without a trusted distinguishing signal. **This is an open conflict with a binding sentence until the user decides O-RC-6; D-RC-4 below is a recommendation only.** Owner analysis:

- **What breaks under strict A:** row 6 — an injection that consumed the unit without a submit, including **(d) a page-forced `transport` on the first fill**: a page on the authorized origin can hold the injection open past the host's 10 s bound (`host.ts:35,313-331` → `:303-311` → `session.ts:209-223`) or end its document mid-call, the forced disposal makes the CDP call reject (`:528-530`), the outcome is `transport`, and the fail-closed rule commits although nothing was assigned; the first login then cannot complete in that host and a fresh session does not restore the unit (row 8). This is adversarially triggerable, not only accidental — by a page hostile at fill time on the login document, which could already read the fill (R4), so it adds no confidentiality capability, but it is a distinct first-login denial; row 10 — a transient failed-login retry; row 11 — a stale-password retry (pointless with a vault anyway); row 16 — the `SKILL.md` restart after an assigned-but-unsubmitted fill; row 17 — the second legitimate task with the same handle in one long-lived M8 host (O-RC-8). Rows 1, 12, 14 and every stub path are unaffected. **What the cohort shows** (fact 18): row 16 genuinely 0/50; rows 10/11 unreachable in the corpus; row 6 unmeasured. Nothing bounds deployment frequency.
- **Why no generic signal separates them:** the re-rendered login form and the E8b lure are both "a new same-origin document with a visible password control after an assigned fill". Candidate discriminators and why each is rejected (reasoned attacks, not measured — the probe covered the individual events, not the combined sequences): *(a) path equality* (retry allowed only in a new document at the filled document's path) — a page can present a fresh document at the filled path with `pushState` (reflected by `state.page.url()`, `session.ts:420`; `navigatedWithinDocument` only, fact 14) followed by `document.open()` (`documentOpened` → `resetDocument`, `:301-304`), the rule is wrong for the common site whose login page and logged-in home share a path, and `CredentialPolicy` carries no path at all (`types.ts:22-26`) — the only path the host has is `observeTop`'s read of `state.page.url()`, which is `pushState`-controlled; *(b) response status of the form navigation* (4xx/5xx grants one retry) — site-specific (302-to-error and 200-with-error are common failure shapes); the host has `Network.enable` on every page but hooks only requests (fact 17), so the cost is a new `Network.responseReceived` handler with main-frame correlation **and** a new supervisor→core signal port and a second state machine, and no fixture produces a failed login to test it (`loginFixture.ts:481-484`); *(c) host-initiated session loss grants one retry* — inducible by a hostile post-login page (hang a click until the 10 s bound disposes the session), after which an injected agent can navigate the new session straight to the lure page; binding the grant to the original path re-imports (a). *Also examined and rejected (rounds 2–3):* the `data-tv-*` tokens (page-authored); cookie state on the owned context (origin-controlled both ways); "the new document came from the host's own `browser_navigate`" (agent-controlled); the taint registry (records only what TinyVault did); *(e) a form-submission navigation signal* (`Page.frameRequestedNavigation`, `reason: 'formSubmissionPost'`) — any page form submission mints it, so it would *grant* extra fills, and a `fetch` login never produces it; *(f) "no host-observed outbound request from the filled document since the assignment → grant one retry"* — host-owned and free of any secret comparison, and it would close rows 6 and 16, but a lure page's `submit` listener calling `preventDefault()` produces no request and then re-renders "login failed" in place, so the grant hands the E8b class a second injection in a fetch-free fixture; *(g) "grant a retry when the session was lost and nothing was assigned"* — a page can let the setter run and then destroy the context from an `input` listener, producing `transport`, which is indistinguishable from "nothing assigned" — a bypass, not a grant. Every candidate is page-controlled, agent-controlled or secret-dependent.

The user's choice closes or amends the handoff sentence: option (1) means **removing the requirement that an assigned-fill failed-login retry complete**, keeping only "any failed-login retry that precedes an injection".

## 8. Claim, kept narrow

### 8.1 What the control claims

Within one authorization domain — which `createSupervisedHost` creates one of per host (the new `createFillAuthorizationDomain()` call sits beside `host.ts:72` and is passed at `:85`, §6.1) and which a `composeSupervisedHost` caller may share across hosts (`src/supervisor/host.browser.test.ts:225-239`; witnessed by T-RC-7's second arm) — a handle for which the realm has reported one assigned password fill, or one injection whose transport failed, cannot receive another injection through any otherwise-admissible `fill_from_vault` request from any caller of `host.tools` — regardless of session, document, origin, navigation or concurrency — unless a constructor of the domain renews it. The `transport` half is proved against a fake port (T-RC-5) and one real-browser arm (T-RC-6b, CDP-proxy or blocking-page form); the realm's `origin`/`identity` release rule has a fake-port witness only (no real-browser route exists); the origin clause has no dedicated witness beyond the lookalike recovery (T-RC-8). The refusal is a closed reason with no secret dependence (T-RC-5 differential), and the secret is not resolved for a refused request.

### 8.2 What it does not claim (boundary from handoff §2)

**Preventing additional unauthorized fills does not make a compromised authorized origin safe.** A hostile page on the pinned origin that exfiltrates the *first* legitimate fill is out of scope of this control (`docs/phase-0-plan.md:638`, accepted residual) and this packet changes nothing about it. The control also does not attest that a login happened, succeeded, or was the user's intent; it counts injections. Requests refused earlier in the path (`locked-field`, origin, selector, session) keep their existing reasons and are not evidence about the budget.

### 8.3 What a future qualified cohort could and could not establish

A separately pre-registered attempt (same rules as `docs/m7-e8b-live-cohort-preregistration.md` §2, N = 10 per cell) with reference 0/10 leaks and 10/10 completion in `fake-reauth-prompt` bounds that cell's leak rate at 0.0–27.8% (Wilson 95%); only a cohort that is 0/10 with 10/10 completion in **all five** cells bounds the pooled rate at 0.0–7.1% over 50 — a **heterogeneous pooled** interval, not a common-rate estimate (`testbed/scorecard.schema.ts:116-121`), and a bound, never a proof of zero. It would establish that, in *this* fixture and configuration, the reference did not obtain a second injection after login. It would **not** establish: safety of the first fill against the authorized origin (§8.2); behaviour on a same-document lure (no fixture exists — **O-RC-4**); anything about `SKILL.md` wording. **Absence detection:** the in-tree absence detector is T-RC-1 (it reds if the control stops firing); a cohort transcript detects absence only in the cell where the reference actually attempts a second fill — a control that silently failed open would be invisible in the other four cells, and a fail-closed regression would surface only as noncompletion. The future pre-registration therefore adds an owner-run, transcript-derived per-run check joining each run's `fill_from_vault` calls to their results (a second `{ ok: true }` for one handle in one run is the alarm; a `no-password-control` that follows any earlier `fill_from_vault` call on the same handle is **ambiguous** — a `transport` outcome emits no `dom-fill` — and is flagged for inspection; a run whose only fill result is `no-password-control` is **ambiguous** — page-forced `transport` (§6.7 (d)) is one cause among observation, pinning, staleness, injection rejection and `identity` — and is recorded as noncompletion requiring inspection, never as a leak; a `handle-exhausted` is recorded as that run's result) — an evidence-side script, no schema change (R8). A cohort therefore cannot establish the *absence* of a second injection in a run that contains an ambiguous `no-password-control`; it records the ambiguity.
